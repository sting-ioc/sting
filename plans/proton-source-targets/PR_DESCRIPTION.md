Sting now uses JSpecify for library APIs, consumer declarations and generated contracts, with NullAway checking handwritten and generated bodies in full JSpecify mode. This is a breaking cutover: legacy nullability annotations at Sting boundaries produce migration diagnostics. Running the processor requires Java 21; library and generated bytecode remain Java 17.

Existing dependency-injection behavior and request forms are preserved, including optional bindings, nullable-provider caching, lazy synchronization and runtime null checks. Unmarked consumers remain supported through optimistic boundaries; their implementations and unspecified contracts are outside the checking guarantee.

Please focus review on annotation-independent service matching, nullable storage and inherited generic/array signatures. Around interception retains one narrow suppression for the erased Object-to-T conversion; generated service methods remain checked. Most fixture and golden changes are mechanical annotation migration.

The processor and QA harness use Proton's public Bazel core and QA targets, pinned to [revision 2dec0fee](https://github.com/realityforge/proton/commit/2dec0fee99c5c5b3707f9f8e8b876ec800e2c40b). An ignored local override links the development checkout; CI fetches the immutable revision. The core target provides the jar with its bundled formatter for processor shading. Sting keeps its declared TestNG version first on test classpaths because Proton QA declares an older runner.

The isolated packaged-consumer check compiles against core/JSpecify with only the shaded processor jar on the processorpath, reads inherited nullness from compiled classes, and verifies Java 17 library and generated bytecode. GWT/J2CL work is outside this migration.
